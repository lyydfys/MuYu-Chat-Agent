## 0. 一页摘要

**一句话方案：** 不把 MCA 做成“又一个 AI 工具官网”，而把它做成 **一台设备的说明书**——纸白、电蓝、真机截图、可核对的数字；开屏用项目图标自己的四个点完成一次“融合”，再把页面作为一台设备“点亮”。

三个关键决定：

1. **开屏不借用外部图形语言。** 图标的四个点就是四种能力（本地推理 / 云端 / 图像 / Agent）。四点被“引力”拉回中心、熔成一个四角星、星撑开对话气泡、四点再回弹归位，最后图标缩入导航栏，页面像屏幕一样亮起。整个动作只使用图标自身的几何，不引入粒子星云、3D 球或发光网格。
2. **首屏的“高级感”来自证据，不来自装饰。** 真机截图 + 11.0 tok/s + `v0.4.1 / arm64-v8a / 612.7 MB` + “无需账号 / 密钥本机加密 / Apache-2.0 / Android 8.0+”。没有虚构指标，没有“10× faster”。
3. **先讲边界，再给下载。** 在最终下载区块之前专门放一节“先把边界说清楚”：本地生图是实验性、DSH 是开发预览、612.7 MB 的体积来自哪里、不按机型白名单隐藏入口。这是 MCA 区别于“营销页”的地方。
4. **三个工作台要有证据，不能只有一句话。** DSH 展示官方界面、控制台与六阶段启动链路；生图展示模板卡、工作台与一张真实出图结果；生视频展示画布节点、节点列表、完成态预览与作品库。全部为真机截图。

原型当前状态：`docs/website/index.html` 可直接打开；支持冻结任意开屏帧（`?t=1820&clean=1`）、深链锚点自动跳过开屏（如 `#faq`、`#faq-size`）、静态全页截图（`?skipOpening=1&static=1`）、重播（`?replay=1`）。页面结构为 Hero → 01 四源归一 → **02 三个工作台** → 03 两条路径 → 04 模型 → 05 Local API → 06 边界 → 07 开始 → FAQ。详细参数见第 12 节。

### v4.9 变更（本轮 · 零差异性能优化）

用户要求：**不影响视觉**的前提下再提升性能。这轮先把"零差异"变成可证明的检测，再逐项测试。

#### 一、检测方法：不再依赖截图

之前的像素对比在本项目**不可复现**（同一份 CSS 两次渲染可差 0 到 87,000 px，
原因是 720×1078 截图解码时序不稳定）。基于它的结论两个方向都不可信。

改用**计算样式 + 几何快照**：对全部 1173 个元素记录 29 个影响绘制的属性
（颜色/背景/边框/圆角/阴影/filter/backdrop-filter/transform/字号/显示/位置/内边距/
角形状等）与 `getBoundingClientRect` 几何，逐元素比对。

验证器自身先跑两遍，结果 **完全一致**，证明它是确定性的。

#### 二、通过零差异的三项

| 项 | 结果 |
|---|---|
| **CSS 压缩** | 151.4 KB → **91.2 KB（−40%）**，1173 元素**全属性 + 几何零差异** |
| **注释剥离**（子集）| 151.4 → 106.4 KB，同为零差异 |
| **资源预加载** | CSS + hero 图 `preload`，按定义不影响视觉 |

CSS 压缩只删除注释与空白，不重命名、不合并、不重排，因此**不可能改变层叠**。已用上表证明。

工程处理：`site.css` 保留为带注释的**可读源文件**；生成的 `site.min.css` 才是页面引用的文件。
`check-site.mjs` 增加同步校验，两者一旦脱节就**构建失败**，杜绝手工改 min 文件的常见事故。

```bash
node scripts/minify-css.mjs    # 重新生成
node scripts/check-site.mjs    # 校验是否同步
```

#### 三、被否决的三项（有差异，已放弃）

| 候选 | 实测结果 | 结论 |
|---|---|---|
| 移除 50 个 `backdrop-filter` | 玻璃填充 `rgba(255,255,255,.34–.58)`，背后透出 42–66%，模糊**可见** | 回退 |
| `.g-atmos` 去 `filter: blur()` | 浅色主题差 **3,090 px / max 231** | 回退 |
| `content-visibility: auto` | 文档高度 10,717 → 11,670 / 10,870，**布局跳动** | 放弃 |
| HTML 空白压缩 | 元素数 1173 → **1174**，内联间距被破坏 | 放弃 |

这四项看起来都是"经典优化"，实测全部不满足零差异要求。

#### 四、真实收益

| 指标 | 前 | 后 |
|---|---|---|
| 下载的 CSS | 151.4 KB | **91.2 KB（−40%）** |
| CSS 首屏阻塞字节（gzip 估算）| ~27 KB | **~16 KB** |
| 关键资源 | 无提示 | CSS + hero 图预加载 |
| 视觉差异 | — | **0（1173 元素全属性 + 几何）** |

保留 `site.css` 源文件不影响线上，因为它不再被页面引用。

#### 五、必须说明的测量局限

**墙钟时间在本机不可用于排名**：对同一改动测两轮曾得出 −9.9% 与 +11.1% 的相反结论，
单轮内波动达 25%，大于被测效应本身。因此本轮**不报告"快了多少秒"**，只报告
可复现的字节数与元素级零差异结论。

### v4.8 变更（本轮 · 320 / 360 / 390 窄屏定位）

上一轮只测到 491px（本机 headless 的视口下限）。这次用 **iframe 精确定宽**把 320 / 360 / 390
三个真实手机宽度全部测完。

#### 为什么必须用 iframe

本机 headless 有约 491px 的视口下限，`--window-size=390` 实际得到 491px 视口。所以之前
"390px 截图"其实是**491px 布局裁到 390**，右侧内容看起来被切，是测量假象而非页面缺陷。

iframe 会建立自己的布局视口，媒体查询按 iframe 宽度求值——这是唯一可靠的办法。

#### 三档宽度实测

| 宽度 | scrollWidth | 横向溢出 | 超边元素 |
|---|---|---|---|
| **320** | 320 | **0** | 3（`CODE` ×2、`t-str`，均在容器内被裁切）|
| **360** | 360 | **0** | 1（`CODE`，被裁切）|
| **390** | 390 | **0** | **0** |

`scrollWidth` 与视口**精确相等**，无横向滚动。

其中超边的 `CODE` 是代码块内部的等宽文本，父级 `overflow-x: auto` 允许它横向滚动——这是
代码块应有的行为，不是缺陷。

### v4.6 变更（本轮 · 手机端审查与横向滚动缺陷）

用户问"目前做了手机版的适配了吗"。因为先前只有"有 media query"这种间接证据，这次做了实测。

#### 结论：适配已做，但存在一个全站横向滚动缺陷

手机端**布局本身是正常的**：

| 项 | 状态 |
|---|---|
| 导航栏折叠为汉堡菜单 | 正常 |
| Hero 竖排（标题 / 正文 / 按钮 / 版本号 / 规格表）| 正常 |
| 手机截图居中、图注完整 | 正常 |
| 卡片单列堆叠 | 正常 |
| 三主题 | 正常 |

但**所有宽度**都存在横向滚动——不只是手机：

| 视口 | scrollWidth | 溢出 |
|---|---|---|
| 504 | 534 | **+30px** |
| 682 | 723 | **+41px** |
| 882 | 935 | **+53px** |
| 1182 | 1253 | **+71px** |
| 1422 | 1507 | **+85px** |

溢出量随视口**成比例**增长，这是关键线索。

#### 定位过程（多次被骗）

| 步骤 | 结论 | 是否可信 |
|---|---|---|
| 列出 `getBoundingClientRect` 超边的元素 | 只有 `.start-watermark` | **错**——绝对定位元素即使被父级裁切，rect 仍报原始位置 |
| 逐个隐藏 `#page` 的 section | 全部 dropped=0 | **错**——溢出不由单个 section 造成 |
| 隐藏 `#page` | 534 → 504 | 对，但只到这一层 |
| 遍历 `main *` | **0 个元素超边** | 说明不是元素 |
| 查伪元素 | `.section--paper::before` 为 `width:720px; right:-6%` | **对** |

真凶是**伪元素**，`querySelectorAll('*')` 看不见它。`.section--paper` 是
`overflow-x: visible`，那个 720px 光晕挂在右边外侧 6% 处，直接计入文档滚动宽度。

### v3.4 变更（本轮 · 边框圆角）

用户指出"边框圆角没做好"。这次用几何推导定位，发现**两个错误叠在一起**，其中一个是
我自己上一轮刚引入的。

#### 推导：圆角处的边框到底有多宽

CSS 把内层圆角画成**缩小版的圆/超椭圆**，而不是把外边界向内平移。两条曲线因此不同心，
角上的边框一定比直边窄。设外半径 R、内边距 p、内半径 r，沿 45° 的实际边框宽度为：

```
n = 1（圆形）：gap45 = (r + p·√2) − R          （已按 1/(cos+sin) 归一）
```

代入 R=22、p=5：

| 内半径 r | 角上边框 | 直边边框 | 比值 | 观感 |
|---|---|---|---|---|
| **17px**（我上轮"精确嵌套" 22−5） | 3.53px | 5.00px | **0.71** | 角上明显偏窄 |
| **18px**（参考值） | 4.24px | 5.00px | **0.85** | 接近均匀 |
| **19px**（理论等宽） | 4.95px | 5.00px | **0.99** | 完全均匀 |

**错误一**：我上轮把 `inner = outer − padding`（22−5=17）当成"精确嵌套"，还写进了文档
表扬自己。实际上这条教科书规则会让角上边框只剩 3.5px。

**错误二**：我同时给边框加了 `corner-shape: superellipse(2.4)`。超椭圆的角更"满"，
与外层圆形内屏搭配时挤压更剧烈：

| 组合 | 角上边框 | 比值 |
|---|---|---|
| 超椭圆2.4 外 / 超椭圆2.4 内（R22/r17） | **1.77px** | **0.35** |
| 圆形 外 / 圆形 内（R22/r18） | 4.24px | 0.85 |

**超椭圆让问题恶化一倍。**

#### 修法

| 项 | 改为 |
|---|---|
| 设备边框 corner-shape | **round**（圆形），与参考一致 |
| 外 / 内半径 | **22 / 18**（参考原值） |
| 页面卡片 | **保留 `superellipse(2)`** |

为什么卡片保留超椭圆：卡片没有嵌套的圆角子元素，不存在"边框宽度"这回事，超椭圆只让
轮廓更舒服。**超椭圆只在"有嵌套"的地方才有害**——这是本轮最有用的一条结论。

#### 关键发现：区块背景把环境整个盖住了

第一次加强背景后，饱和度只从 0.049 升到 0.056。原因在纵向扫描里：

```
y= 287  L=242.3
y= 574  L=242.3      <- 三个深度上数值完全相同
y= 861  L=242.3
```

### v2.6 变更（本轮）

针对"圆角不对、玻璃质感不到位"，重新查资料并重做。核心发现：**这两件事都有可量化的
技术答案，而我之前都是凭感觉调参。**

#### 一、圆角：圆角弧不是超椭圆

| 事实 | 来源 |
|---|---|
| iOS 图标圆角 = 宽度 **22.37%**，smoothing **60%**，是超椭圆不是圆角矩形 | [Squircle.js · Apple 设计](https://squircle.js.org/blog/squircles-in-apple-design) |
| `border-radius` 只能画圆弧；`corner-shape: squircle` = `superellipse(2)` 才是超椭圆 | [Squircle.js · CSS 2026](https://squircle.js.org/blog/squircles-in-css) |
| 圆弧在直边与弧的接点有 **G1 不连续**（曲率突变），这是"廉价感"的来源 | 同上 |

**实测证明几何真的变了**（400px 方块、80px 圆角，沿 45° 对角线测到边界的距离）：

| corner-shape | 实测 | 理论圆弧 |
|---|---|---|
| `round`（原状） | **23.0px** | 23.4px ✔ 吻合 |
| `squircle` | **13.0px** | — 向内收 10px |
| `superellipse(2.4)` | **10.0px** | — 设备更方 |

**同时修掉的圆角硬伤：**

| 问题 | 修法 |
|---|---|
| 全站圆角值是 8/10/12/14/20/24/26/31/32/38px 散值，无体系 | 建立 7 级尺度（8/12/16/22/28/36/999） |
| `.source`、`.ws-stage` 圆角为 **0**，是页面最大的面板却唯一直角，squircle 无从作用 | 补 22px 并应用超椭圆 |
| 嵌套圆角不满足 `inner = outer - padding` | 手机外框改为 `calc(var(--radius-l) - 5px)` |
| 工作区分成两张浮卡，中间出现接缝 | 合并为**一整块**：外层承担玻璃与边缘光，内半块去掉边框与背景 |

#### 二、玻璃质感：不是层数不够，是**色调没有落差**

这一轮测量推翻了我上一轮的判断。上一轮我加了 6 层结构，但实测：

```
页面背景 = 248    面板填充 = 242    深部 = 208
```

**面板比页面还暗**，而参考实现的原则写得很清楚：

> "浅色玻璃是**更白、更亮**，不是更暗"
> "浅色玻璃需要一个**有颜色**的浅底，否则白玻璃在纯白上没有任何东西可透"
> "浅底上亮边要**偏冷灰**，纯白会看不见"

按此修正：页面底色加入真实色相（蓝/紫/青三团光晕），填充 alpha 从 .92 降到 **.62**。

**为什么是 .62——这是算出来的：**
```
填充 = a*255 + (1-a)*231
a=.92 -> 253   （距纯白仅 2 级，白边无处可亮）
a=.62 -> 246   （留出 9 级给高光）
```

**三次失败的边光尝试（都被测量否掉）：**

| 尝试 | 结果 | 原因 |
|---|---|---|
| 单一 180° 渐变 | 与填充同亮 +0.3 | 只能点亮上下边，左右拿到中段透明色 |
| 叠加 180°+90° 双层 | **数字完全不变** | 两层合成，垂直层的冷中段压住了水平层 |
| conic 但色标偏冷 | +1.0 | 色标亮度 ~240 **低于**填充 248，成了暗缝 |

**最终方案：conic-gradient 环形边缘光**——边缘光是"绕周长的角度函数"，不是 x/y 函数。
除底边外每个色标都亮于填充（镜面反射只会抬高表面，不会低于自身透射）。

**实测（隔离测试台，空面板）：**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 页面 / 填充 / 边光 | 245 / 242 / 步进，无峰值 | **231 / 248 / 253** |
| 填充比页面 | **暗 -3** | **亮 +16.9** |
| 边光比填充 | +0.3（不存在） | **+5.0**（真实高光） |

#### 三、诊断手法上的教训

- 用 `max()` 采样"边光"，只能发现比填充更亮的边，**暗边光必然漏检** —— 三次改动都报
  +0.3 就是这个原因，换成直接采样边缘像素带才看出问题。
- 页面内容填满面板，导致"内部亮度"实际测的是子元素。改用**隔离测试台**（空面板 +
  真实 site.css）才拿到干净的读数。
- 对比度脚本曾因函数名写错（`BG(` vs `bgOf(`）在玻璃主题抛出异常，输出 `glass: no
  data` 却仍然打印 **PASS** —— 空集上的通过等于没测。已修正并加了 `no data` 判据。

**玻璃为什么必须是多层的：**

| 层 | 作用 | 少了它会怎样 |
|---|---|---|
| `background-image` 的 140° 多段渐变 | 面板受光不均，像真玻璃 | 单一实色 = 塑料板 |
| `::before` 的 1px 渐变边（`mask-composite: exclude`） | 上缘受光、下缘转冷 | 用 `border` 时四边同色，看不出厚度 |
| `::after` 的内层柔光（两道 radial） | 光被"收"在边缘内侧 | 玻璃失去体积感 |
| 双内阴影 `0 1px #fff/.95 inset` + `0 -1px 冷色/.22 inset` | 浮雕（bevel） | 面板贴在背景上，不"浮"起来 |
| `.g-gloss`（真实 DOM，跟随 `--gx/--gy`） | 随指针移动的高光 | 玻璃是"死"的，没有液态感 |
| `.g-atmos`（共享氛围层，blur 8px） | 提供可被折射的环境 | 玻璃后面是空白色，不折射任何东西 |

## 1. 定位：为什么不能照着 CC Switch 做

CC Switch 的页面主语是 **“统一管理多个 AI 编程 CLI 的配置”**：用户已经在用 Claude Code、Codex、Gemini CLI 等工具，官网要解决“在哪里管理它们”。这天然长成一个桌面工具站：工具清单、配置示意、下载、功能格子。

MCA 的页面主语完全不同：**“模型运行在这台手机上”**。用户要的不是再管理一个配置文件，而是拿回模型、密钥和对话的所有权。因此本方案主动放弃“工具站/SaaS 首屏”的语法：

| 维度 | CC Switch（参考对象的定位） | MCA（本方案） |
|---|---|---|
| 页面主语 | 多个 AI 编程工具的统一配置 | 一台手机上正在运行的模型与工作台 |
| 使用场景 | 桌面开发工作流 | 手机、离线、随身 |
| 首屏证据 | 工具列表 / 管理界面 | 真机截图 + 断网事实 + 版本/体积 |
| 视觉语言 | 工具型产品官网 | 纸白仪器手册：单一电蓝、细线、等宽小字、章节规则 |
| 动效 | 品牌展示 | 图标四源归一 → 端侧成形 → 图标入导航 → 页面点亮 |
| 结尾 | 功能清单 + 下载 | 先讲边界 + 体积解释 + 下载 |
| 情绪 | “都交给我管理” | “东西在你自己手里” |

**不复制清单：** 版式、导航结构、首屏构图、配色、图标、文案、截图排列、动效节奏。相同点只在于“官网需要让用户理解产品并完成下载”这一层产品功能。

### 三条设计原则

1. **证据优先。** 每一句形容词旁边尽量有可核对的东西：截图、版本、体积、状态、文档链接。没有数据就不写“最快/最强”。
2. **一个强调色。** 品牌蓝 `#1A73E8` + 纸白 `#F8F9FA`。暗场只属于开屏和 Local API；页面主体保持纸白。没有紫色渐变、没有第二品牌色。
3. **动效只讲一件事。** 四个来源合成一个工作台；其他交互（章节出现、路径切换、复制）只做必要的状态反馈，不做持续漂浮、不做滚动劫持。

## 2. 品牌叙事：四源归一

### 2.1 图标拆解

项目 launcher 矢量（`app/src/main/res/drawable/ic_launcher_foreground.xml`）由三部分组成：

- **对话气泡**：一次对话，也是整个工作台。
- **四角星**：端侧核心。四角星不是装饰，是“在设备内完成的那一步”。
- **四个点**：四个来源/四种能力。它们的位置本身就不对称——这是图标已有的性格，不要改成对称。

在本方案中，四个点对应产品架构：

| 图标元素 | 产品语义 | 页面落点 |
|---|---|---|
| 左上点 | 本地推理 MNN / GGUF | 01 本地推理 |
| 右下点 | 云端 OpenAI / Anthropic | 01 云端接入 |
| 左下点 | 图像与视频 | 01 图像与视频 |
| 右上点 | Agent / Local API | 01 Agent 与 API |
| 四角星 | 端侧核心 | 开屏融合点 |
| 气泡 | 对话/工作台 | 开屏成形、页面点亮 |

### 2.2 开屏叙事（一句话）

> 四个来源被拉回这台设备，熔成一个核心；核心撑开一次对话；四个点回到原位；图标变成导航栏里的 logo；页面亮起。

这不是“logo 动画 + 页面淡入”，而是一次连续变形：**点 → 星 → 气泡 → 点 → logo → 页面**。进入和退出使用同一组点，形成闭环。

### 2.3 文案锚点

- 首屏：**“断网，也能用。”**（主张；蓝色句号是品牌点）
- 能力：**“四源归一。”**（把开屏的四个光点解释成四种能力）
- 路径：**“同一条消息，两条路径。”**（本地/云端对照）
- 模型：**“模型，是你选的。”**（不锁来源）
- 开发者：**“它还是一台，能对话的服务器。”**（Local API）
- 信任：**“先把边界说清楚。”**（实验性/体积/兼容）
- 收尾：**“把 AI，拿回来。”**

语气规则：短句、动词开头、少用形容词；不用“赋能、一站式、极致、颠覆”；承认未完成；不写感叹号。

## 3. 视觉系统

### 3.1 关键词

**仪器手册 / 实验记录 / 纸白 / 电蓝 / 细线 / 等宽小字 / 真机证据 / 章节编号。**

不是一个“AI 创业公司落地页”，而是一台你买回家的设备的说明书：有编号、有规格表、有 `FIG. 02`、有边界说明。

- 暗场小字最低 `--night-muted`，不再使用 `#5F6771` 一类 3.3:1 的灰。
- 不用第二个强调色。状态差异靠文字、边框、虚实线，不靠红绿黄。

### 3.3 字体

**原型使用系统字体**（Windows 下实际是 Microsoft YaHei / Segoe UI），这是有意的：

- app 本身就用系统字体，官网跟随，避免中文 Webfont 的 300KB+ 负担。
- 生产建议：中文用系统栈 `PingFang SC / HarmonyOS Sans / Noto Sans CJK / Microsoft YaHei`；拉丁用自托管 `Inter` 子集；等宽用 `IBM Plex Mono` 或系统 `Cascadia Mono / SF Mono`。
- 不引入一套只用于标题的中文展示字体；标题的重量感靠字号、字距和留白建立。

字阶：

| 角色 | 桌面 | 移动 | 行高 / 字距 |
|---|---|---|---|
| Display（H1） | 88–92px | 44–64px | 1.03 / `-0.035em` |
| H2 | 44px | 34px | 1.18 / `-0.025em` |
| H3 | 25px | 22px | 1.3 / `-0.02em` |
| Lead | 17px | 15.5px | 1.78 |
| Body | 14.5–16px | 13.5–14.5px | 1.75 |
| Meta / mono | 11–12px | 11–11.5px | `0.06–0.14em`（全站可见正文与标签字号下限 ≥11px） |

### 3.4 网格与节奏

- 容器 1240px，12 列，24px gap，页面左右 32px；1440 视口下内容落在 132–1308px。
- Section 垂直节奏 104/112px；移动 72/80px。
- **章节规则**：`编号 + 细线` 横贯内容宽度，再接 H2。它是全站最强的结构符号，也是“说明书感”的来源。H2 必须与正文左边缘对齐（原型已修正为 132px 对齐）。
- 卡片只用 1px 线 + 纸白，不用投影堆叠；投影只给手机、终端、截图框三个“实物”。

### 3.5 组件语言

- **按钮**：999px 胶囊；主按钮蓝底白字；无渐变；hover 只深一级；按下位移 1px。
- **规格表**：固定列宽、上/下细线、无斑马纹；hover 只给极浅底色。
- **Trace**：左侧节点 + 连接线；当前推理行用 2px 蓝色内阴影标记；云端路径用灰底 + `NETWORK`。
- **终端**：暗场里唯一的高对比面板；`$` 提示、蓝/白两色语法、复制按钮。
- **Datasheet**：6 列 mono 标签 + 值；发布信息是“证据”而不是装饰。
- **状态 chip**：小圆点 + 文字（稳定/实验/条件可用）；不靠颜色单独传达。
- **图标**：只使用项目图标 + 4 个 1.5px 线性图标（星/云/图/终端）；不引入插画、3D、emoji。

### 3.6 明确不做

玻璃拟态、霓虹渐变、紫色光晕、3D AI 球、粒子星云、自动播放带声音的视频、滚动劫持、自定义光标、满屏卡片浮起、虚构 benchmark、假用户头像、Cookie 弹窗（本站不设 Cookie）、自动深色模式。

**关于深色模式：** 首版主动不做自动深色。app 的截图是浅色；开屏的“暗 → 亮”是品牌叙事；如果跟随系统变暗，会出现“暗场开屏 → 暗色站点”和浅色截图刺眼两个问题。若未来要做，作为手动主题，并重新出深色截图、重新设计开屏的落点。

### 5.2 关键参数（与原型一致）

- 图标坐标空间：`viewBox="20 20 68 68"`，尺寸 260px（移动 210px）；四角星中心 `(54,50)`。
- 四个点（原始图标坐标）：`(36,38,r3.5)`、`(72,62,r3.5)`、`(42,68,r2.5)`、`(66,36,r2)`。
- 四个来源的起始位置：从中心沿“该点方向”外推 **56 单位**；角度由图标四点本身决定，不做对称化。
- goo 滤镜：`stdDeviation 1.15`，alpha 矩阵 `... 22 -10`；仅在 `t <= 1360ms` 融合阶段挂载，融合完成后立即移除 `filter` 属性以降低合成开销。
- 气泡描边：`pathLength="1"`；`stroke-dashoffset 1→0`，270ms；填充 200ms，fill-opacity 0.98。
- 星形：`easeOutBack`，轻微过冲；旋转 -52°→0。
- 软边光圈：mask 径向渐变，**260px 对称羽化** + 暗场 `opacity` 消隐；`--iris` 从 `-260px` 到 `对角×0.68+320px`，420ms，消除四角暗圈残留。
- 图标归位：目标点来自 `getBoundingClientRect()` 的导航品牌图标；缩放 1→30/260；导航品牌在落点淡入，避免“两个 logo 并排”。
- 降级：`prefers-reduced-motion` / `saveData` / URL 深链锚点 → 直接显示页面；`sessionStorage` 记录本次会话已播放；3.4s 失败保护；无 JS 时开屏层默认 `display:none`。

### 5.3 为什么用 SVG + 自写时间轴

- 整个开屏只有一个内联 SVG（约 2KB 结构）+ 约 6KB gzip 的 JS；没有 GSAP/Lottie/Three.js。
- 自写 `render(t)` 是**时间的纯函数**，所以可以用 `?t=1820&clean=1` 冻结任意帧做评审与截屏；生产也可以用它做自动化视觉回归。
- 共享元素归位依赖对导航 logo 的实时测量，Lottie/视频做不了；goo 融合需要 SVG 滤镜或 canvas，SVG 更轻。
- 不用视频：视频 2–4MB、4K 不锐利、无法响应主题/尺寸/跳过、会拖慢 LCP。

### 5.4 性能与可访问性

- 开屏只操作一个 260px SVG 和约 20 个元素；无 canvas、无 WebGL、无持续 rAF 循环（2.66s 后停止）。
- 滤镜只在 `t <= 1360ms` 区间挂载，融合完成后自动解绑 `filter` 属性，减少合成开销。
- LCP 目标是 Hero 的 H1 文本；开屏层不阻塞首帧，H1 在 DOM 中先绘制。若真实测量显示 LCP 被开屏拖慢，首访延迟 300ms 再播放，或直接不播。
- 可访问性：开屏为装饰，`aria-hidden` 于图形与文字；页面在播放期间 `inert`；跳过按钮可聚焦；Esc 可跳过；无声音；减弱动效时完全不播放；不劫持滚动（播放时 `body overflow:hidden`，结束恢复）。
- 不自动循环、不无限脉冲、不做视差抖动。

### 5.5 这个动效“不做什么”

不做粒子爆炸、不做镜头抖动、不做 RGB 故障、不做扫描线、不做 3D 旋转、不做声音。四束光、一个核心、一次成形，够了。
