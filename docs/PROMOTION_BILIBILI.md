## 一、四条支柱与各自的证据等级

写文案之前先把每个卖点的真实成色摊开。凡是代码里查不到的东西，一律不进文案。

| 卖点 | 代码核实结果 | 可以怎么说 | 不能怎么说 |
|---|---|---|---|
| **角色扮演** | 支持 `CC_V2` / `CC_V3` / 旧版 JSON；PNG 的 `chara` 与 `ccv3` 两种元数据都解析；备选开场白、群组专属开场白、未知字段全部保留；有世界书和离线知识库 | 角色卡直接导入，人设不会掉字段 | 不提"群聊"，因为还没有 |
| **生图** | `stable-diffusion.cpp` 通路，带进度与取消；MNN-Diffusion 需通过 1 步运行时校验才可选；QNN 图像包按实验包处理 | 断网出图、给角色画立绘 | 不提速度排名，不提"稳定可用"，不提 SDXL 质量 |
| **API** | 本地 OpenAI 兼容服务，`127.0.0.1:11435`，支持 SSE 流式、视觉输入、`/v1/models` 带 `vision_ready` 扩展字段 | 手机能给电脑上的软件当后端 | 不说"公网可用"，默认只监听本机 |
| **NPU** | QNN/QAIRT 通路真实存在，但有七级状态门禁 | 按状态机口径讲，给日志 | 不说"有骁龙就能用"，不说"NPU 加速稳定" |
| **KV 缓存** | `cache_type_k` / `cache_type_v` 支持 f32、f16、bf16、q8_0、q4_0、q4_1、iq4_nl、q5_0、q5_1；量化 V 缓存强制要求 Flash Attention；另有 `cache_reuse`、持久化前缀缓存 | 长人设不爆内存；重开对话不用重算人设 | 不要报"省了多少 MB"，除非你实测过 |
| **投机解码** | `spec_type` 支持 `draft-simple`、`draft-eagle3`、`draft-mtp` 和四种 ngram 方案 | 出字速度有提升 | 不报未实测的加速倍数 |
| **MoE 混合推理** | 有 `n_cpu_moe`，把专家层留在 CPU | MoE 大模型也能在手机上跑 | 不承诺具体机型能跑 |
| **MCA llama.cpp 的 GPU** | `core/native` 自建的 llama.cpp 目标没有启用 OpenCL/Hexagon；最终 APK 还会随独立 GenieX AAR 携带其 OpenCL/Hexagon 动态后端，但这不等于 MCA 的纯 llama.cpp 路径已经完成 GPU/NPU 验证 | 暂时不提 | 不能把 GenieX 携带的后端库写成 MCA llama.cpp GPU 已跑通 |
| **LiteRT-LM 运行时** | 真实支持四个后端：`cpu`/`host`、`gpu`/`opencl`、`npu`/`qnn`/`qualcomm`、`google_tensor`/`tpu`；GPU 另有编译缓存的失效与重载逻辑 | 可以宣传，讲"同一个运行时能在 CPU / GPU / NPU 之间切换" | 不要说"GPU 加速已经跑通"，证据不足，理由见下 |

GPU 这个点要分成两个对象看，这是本版最重要的修正。

**MCA 自建 llama.cpp 的 GPU 仍未验收。** 它的 CMake 目标默认没有编进 OpenCL/Hexagon；APK 中出现的 `libggml-opencl.so`、`libggml-hexagon.so` 来自 GenieX 独立插件。除非有针对纯 `llama_cpp` 运行时的真机分配与 decode 证据，否则不要把这些随包后端库写成 MCA llama.cpp GPU 已跑通。

**LiteRT-LM 的 GPU 是真实实现的**，而且这是 MCA 里唯一一条把 CPU / GPU / NPU / Google Tensor 四个后端都接进来的运行时。但我把真机记录翻出来了，2026-09-02 唯一那次 GPU 尝试是失败的。失败原因记在 `docs/experiments/device-smoke/litertlm-chat/accept-litert-gpu-0902/`：

```
LiteRT-LM 文件头/结构无效：section[2] end_offset=2008432640
超出文件大小=380207104，模型包可能被截断
```

文件头声明约 2 GB，实际只下到 380 MB，加载阶段就被拒绝了，根本没走到 GPU。而且那次跑的是 debug 活动，不是生产界面，按项目自己的验收政策只能算诊断、不算验收。

所以 LiteRT 这条线可以宣传，但口径收到"运行时支持多后端"为止，不要收到"GPU 已经跑通"上。想拿到 GPU 的发言权，补三件事就行，成本都不高：

1. 重新下一份完整的 `.litertlm` 模型包，上次的失败就是下载不全
2. 用生产 `MainActivity` 跑一次，别用 debug 活动
3. 拿到 `backend=gpu` 和实测 tokens/s

**另外，那次失败本身是个好素材。** 应用拿到一个被截断的模型包，没有崩溃，而是把声明大小和实际大小都报了出来，精确到字节。这正好演示了项目"只按具体运行时条件拒绝、不按机型拒绝"的设计原则——是包坏了，不是你的手机不行。这种细节做成内容，比任何自我吹捧都有说服力。

## 二、把技术点翻译成观众能感知的东西

NPU、KV 缓存、MoE 这类词，直接说没有传播力。观众不关心机制，只关心自己的体验变了什么。所以每个技术点都要配一句人话。

| 技术点 | 观众感知到的变化 | 视频里的说法 |
|---|---|---|
| KV 缓存量化 | 人设写得长、世界书条目多，也不容易炸内存 | 它把对话缓存压缩了，所以人设写长一点也不容易爆内存 |
| 持久化前缀缓存 | 新开一个对话，人设不用重新读一遍 | 换一个对话，人设不用重新算，第一句话来得更快 |
| Flash Attention | 长对话更稳 | 长对话不容易崩 |
| 投机解码 | 出字更快 | 开了投机解码，出字有提升 |
| `n_cpu_moe` | MoE 大模型能在手机上跑起来 | 专家层放 CPU，注意力层走加速器，这样大模型才塞得进来 |
| NPU | 生图和视觉真的用上了专用硬件 | 必须带状态机口径，见第六节 |
| API | 手机能给别的软件当后端 | 手机变成一个接口，电脑上的软件直接连 |
| LiteRT-LM 多后端 | 换模型不用换应用，快慢自己挑 | 同一个运行时，CPU、GPU、NPU 三档可以切 |

一句话原则：**先讲体验，再给术语。** 顺序反了，观众划走。

## 三、定位与主张

主定位：

> **一部手机，装下一整套本地的 AI 角色扮演和生图。**

副定位（技术向内容用）：

> 断网可用，开源免费，NPU、KV 缓存、本地接口全都摊开给你看。

三条支柱，每条都能当场验证：

- **端侧跑完**。飞行模式下对话、看图、出图都正常。
- **卡能直接用**。你攒的角色卡拖进去就行，V2、V3、PNG 元数据都认。
- **一个 App 走完整条链路**。聊天、导入角色、给角色配图、给别的软件提供接口，都在同一个应用里。

## 四、话术改写法则

上一版定下的规矩继续用：不点名任何竞品，把"比别人强"改写成"你能做到什么"，对比交给观众。

| 原本想说的 | 改成 |
|---|---|
| 不像别的工具要配一台电脑 | 一部手机独立完成，不需要第二台设备 |
| 别人的角色是官方预设的 | 你自己的角色卡，拖进去就能用 |
| 别人在云端读你的对话 | 飞行模式下照常聊天 |
| 别的工具只会出图 | 聊完顺手给角色画一张立绘 |
| 比同类快 | 512×512、20 步实测 12 到 14 秒 |

**能报绝对值就报绝对值，别给排名。** 你现在的实测数字（UNet 约 184 到 186 毫秒每步、20 步约 12.8 到 14.5 秒、QAIRT 视觉首 token 513 到 635 毫秒、解码 20.6 到 22.5 tok/s）都是可复现的，这些就是你的弹药，比任何"吊打"都有用。

## 五、内容矩阵：主线四期 + 技术深度五期

四条支柱不能挤在一期里讲完。分两条轨走：主线抢流量，深度立人设。两轨交替发，深度内容反哺主线的可信度。

### 主线轨（面向泛用户，抢流量）

**第 1 期｜角色卡搬家**
《我把攒了三年的角色卡，全搬进了手机》

- 0:00–0:15 飞行模式，打开应用，角色已经在说话
- 0:15–1:00 拖进一张 PNG 角色卡，人设和开场白自动填好
- 1:00–2:30 断网对话，触发世界书
- 2:30–4:00 顺手给这个角色生成一张立绘
- 4:00–5:30 主动说短板（没有群聊、Live2D、语音朗读），引导三连

**第 2 期｜手机出图**
《手机本地给角色画立绘，什么水平？》

这一期是你要的生图主推。要点是把落点放在"给角色配图"上，不要做成通用生图评测。素材可以挑这几个角度：

- 同一段剧情，连着给三个角色各画一张
- 展示图生图，把角色立绘改一个场景
- 出图之后把图再喂回去让它描述，走完"出图 → 看图 → 再聊"的整圈
- 全程飞行模式，状态栏网络速率露在画面里

速度可以讲，但用绝对值，别跟谁比。

**第 3 期｜断网极限**
《手机上的酒馆，断网能玩到什么程度》

一期纯验证向视频。从装好模型开始全程不联网，把聊天、看图、出图、世界书全部走一遍。这一期几乎不需要剪辑技巧，观众要的就是"真的没联网"这个事实。

**第 4 期｜全链路**
《角色卡 + 世界书 + 生图，一个 App 全本地跑通》

把四条支柱串成一次完整体验：导入卡、加载模型、开始对话、触发世界书、生成配图、导出角色卡。

### 技术深度轨（面向懂行的人，立人设）

**深度 1｜KV 缓存**
《手机跑大模型最容易忽略的一层：KV 缓存》

这是我最看好的一期，因为它是你被低估最严重的资产。可讲的内容：

- 支持哪些缓存类型（f32 / f16 / bf16 / q8_0 / q4_0 / q4_1 / iq4_nl / q5_0 / q5_1）
- 量化 V 缓存为什么必须搭配 Flash Attention，讲清这个约束背后的原因
- 持久化前缀缓存：重开对话不重算人设，现场对比冷启动和命中缓存的差别
- `cache_reuse` 的阈值是干什么的
- 长人设 + 多世界书条目下，量化前后内存占用的实测对比

这类内容在中文端侧圈子里很少见，做出来容易建立权威感。

**深度 2｜NPU 证据**
《手机 NPU 到底行不行，我把日志摊开给你看》

沿用七级状态口径：设备支持、运行时找到、可加载、包完整、图元数据就绪、冒烟通过、NPU 真的执行了。每讲一级就摊一次日志。别怕说"这一步还没通过"，这恰恰是你区别于其他内容的地方。

**深度 3｜本地接口**
《把手机变成 OpenAI 接口，给电脑和别的软件用》

面向开发者和折腾党。演示第三方客户端接入、SSE 流式输出、`vision_ready` 字段怎么用。受众窄，但这期的观众质量最高，是贡献者和真机测试者的主要来源。

**深度 4｜MoE 与投机解码**
《MoE 大模型怎么塞进手机》

讲 `n_cpu_moe` 的分层策略和 `draft-mtp` 投机解码。受众最窄，但话题性最强。

**深度 5｜运行时与后端**
《一个 App 里塞了四个推理引擎，是怎么选的》

讲 MCA 里并存的四条运行时（llama.cpp、MNN、LiteRT-LM、GenieX-QAIRT），以及 LiteRT-LM 的 CPU / GPU / NPU / Google Tensor 四后端切换。这一期放在最后，作为技术深度轨的收尾。

注意口径：LiteRT 讲"支持多后端"，不要讲"GPU 已经跑通"，原因见第一节。

### 对标：B 站同类内容现在长什么样

实地看了同题材的视频，主流是四种形态。

**形态 A｜「GitHub 狠活神器」，最主流，也最值得你切入**

标题长这样：「顶级!!Github 又出狠活神器!斩获 9.6 万 Stars,下载量突破 26 万次」

特征是报 Stars 数当作权威背书，单条片子长度在 **49 秒到 1 分 25 秒**之间，合辑总长 5 到 10 分钟。同一个题材下已经有人做过「手机版 Stable Diffusion,完全离线运行,支持文生图、图生图和图片修复」——直接撞上你的生图点。

**形态 B｜保姆级部署教程**

标题长这样：「【喂饭教程】手把手教你 20 分钟使用 LM Studio 本地部署 Qwen3.5-9B,小白也能轻松拿捏,学不会你来找我(附教程)」

高频句式是「照着做就能跑起来」「全程中文界面,每一步都有屏幕演示」「所有命令和下载地址我都整理好了,点我头像后台领取」。时长中长，8 到 20 分钟。

**形态 C｜酒馆系列化教程，已经成熟**

「【酒馆 SillyTavern 教程】局域网用手机链接酒馆(三十五)[AI女友]」——已经做到第三十五集，说明这个品类有稳定受众和稳定创作者。

**这里有个关键信息：他们的"手机上用酒馆"，指的是手机当浏览器客户端，模型仍然跑在电脑上。** 手机端本地推理这一块，内容是空的。

另外，纯参数式标题也有人做，比如「本地 OmniVoice-TTS 接 SillyTavern(酒馆)-显存 3.5g-语音延迟 4s 左右」。标签体系极其完整：#SillyTavern #酒馆 #TTS语音 #一键启动器 #AI角色扮演 #教程。这个赛道已经有人靠"一键启动器 + 内置 API + 按字收费的语音"变现了。

**形态 D｜显存与参数硬核向**

「GLM-Image 一键包 4G 显存可用」「LTX-2 只需 8G 显存,即可生成电影级 AI 大片」。报显存、报延迟、报步数。

顺带一提，我看到的 Qwen3.8-27B 部署视频里，命令行参数是 `-ngl all -fa on -ctk q4_0 -ctv q4_0 --spec-type draft-mtp`——和 MCA 支持的完全是同一套。也就是说 KV 量化和投机解码在 B 站技术观众眼里，已经是"懂行"的标志，深度第 1 期有受众基础。

**共性公式**

| 要素 | 具体表现 |
|---|---|
| 情绪词 | 顶级、最强、绝了、离谱、真香、狠活、yyds |
| 数字锚点 | Stars 数、显存、耗时、延迟、文件大小 |
| 人群标签 | 小白、普通人、零成本、喂饭 |
| 能力承诺 | 照着做就能跑起来、学不会你来找我、全搞定 |
| 平台覆盖 | 安卓、iPhone 全搞定；手机、电脑、网页三端 |
| 导流 | 三连加关注可见提取码、点头像后台领取、网盘链接 |

**「一键包」「整合包」「一键启动器」出现频率极高。** 中文观众对"下载即用、零配置"的诉求非常强烈。这一点对你有利：别人要发整合包，你是 APK 直接装，一句话就能讲清差别。

**借结构，别借腔调。** 上面那套"顶级!!""狠活""绝了"的语气，和 MCA 的严谨调性直接冲突——而严谨恰恰是你的差异化。所以标题可以借它的数字锚点和人群标签，语气不要跟着走。你可以这样做对照：

| 他们的写法 | 你的写法 |
|---|---|
| 顶级!!斩获 9.6 万 Stars | 斩获 X Stars，我把它跑通了 |
| 太离谱了，绝了 | 实测 12 到 14 秒一张，日志在这里 |
| 秒加载不卡顿 | 断网可用，网络速率为零 |

另外，形态 A 给了一个重要提示：**你想要的 1 分钟视频，正确的形态是"合辑里的一个条目"或者"竖屏单条"，不是横屏正片。** 横屏正片仍然建议 5 到 7 分钟。

## 六、NPU 的说法必须带状态机

这是全文最容易被误用的一节。NPU 是你最强的技术卖点，也是最容易翻车的地方。

**唯一正确的表述方式**，是把这七个状态分开讲：

1. 设备属于支持的档位
2. 找到 QNN/QAIRT 运行时文件
3. 原生加载探测通过
4. 模型包结构完整
5. 图元数据（张量名、类型、形状）就绪
6. 一次冒烟运行通过
7. 这次真实请求的日志证明 QNN/HTP 图执行了

只有第 7 级成立时，才能说"这次用了 NPU"。第 1 到第 6 级都不算。

反例，绝对不要出现：

- 因为手机是骁龙旗舰，所以是 NPU 加速
- 支持 NPU 加速（不限定条件）
- NPU 出图又快又稳

**同时要记住：NPU 是加分项，不是主线。** 普通观众看不懂，也买不到对应机型。它真正的价值是让懂行的人认可你，所以它属于技术深度轨，不要放进第 1 期的标题。

## 七、生图能讲什么、不能讲什么

你要主推生图，方向没问题，但边界得划清。

**能讲**：断网出图、给角色画立绘、模板和风格卡片、图生图、出图后回喂给模型看、图片只在本地。

**不能讲**：速度排名、稳定可用、高分辨率、和桌面端比质量。

**原因**：手机端本地生图目前是存储和散热的游戏，预期一旦拉高，第一次生成就会失望。热度来得快，反噬也快。你手上真正能打的是"给角色配图"这个场景，那是别处没有的链路，不是帧率。

## 八、观众提竞品时的应答预案

你不点名竞品，但观众会提。三种情况提前准备，临时回容易说错。

**问"和某某比怎么样"**

> 那个我没深度用过，不敢乱讲。我这边的情况是：不依赖第二台设备，角色卡直接导入，全部在本机跑。你自己装上试试，哪个顺手用哪个。

**说你不如某产品**

承认具体项，别硬撑。

> 确实，群聊、Live2D、语音朗读我这边还没有，在排期里。我先把端侧跑通和不依赖第二台设备这两件事做完。

**说你抄某个产品**

## 十、发布细则

**分区**：主线轨走科技 — 数码；技术深度轨走科技 — 计算机技术。

**标签**：大模型、端侧推理、Android、本地部署、角色扮演、开源、离线 AI、KV 缓存、NPU。按当期内容取，别堆。

**封面**：手机实拍加一个关键数字，钩子不超过 12 个字。不要满屏文字。

**时长**：分三档，各有各的用途。

| 形态 | 时长 | 从哪进流量 | 干什么用 |
|---|---|---|---|
| 竖屏切片 | 30 到 60 秒 | Story Mode 竖屏流 | 获客，把人导到横屏正片 |
| 横屏主线 | 5 到 7 分钟 | 首页推荐 + 搜索 | 转化，让人真的去下载 |
| 技术深度 | 8 到 12 分钟 | 搜索 + 长尾 | 立人设，吃长尾流量 |

这里有一个反直觉的点值得记住。B 站的完播率不是"看到最后一秒"才算，算法更看「观看时长」和「完播深度」的组合。一条 7 分钟的视频平均被看到 40%（约 2.8 分钟），权重往往高于一条 1 分钟的视频被完整看完（1 分钟）。所以为了完播率好看而把片子压到 1 分钟，反而吃亏。

另外 MCA 的转化路径偏长：观众要去 GitHub 下 APK，再下模型包，再导入，才能跑起来。1 分钟的视频吸引来的是耐心最低的那批人，他们几乎不可能走完这个流程。真正会下载的人，需要看到完整演示。

但"1 分钟以内抓住人"这个直觉是对的，只是它对应的不是总时长，而是**前 3 秒**：

1. 第 1 秒抛问题或亮状态（飞行模式已开，网络速率为零）
2. 第 2 秒给结果（角色已经在说话，或者图已经出来了）
3. 第 3 秒给承诺（后面还会演示给角色画立绘）

之后每 30 秒埋一个信息点，别让注意力掉下去。

**同一批素材剪两个版本**：横屏正片走推荐流，从正片里切 30 到 60 秒竖版发 Story Mode，两个入口吃两次流量。

**第一条视频不要超过 8 分钟。** 新账号权重低，长视频冷启动压力大。等前两条数据稳了再放深度内容。

**发布节奏**：主线和技术深度交替发，不要连着发两期技术内容，会掉流量。建议顺序是主线 1 → 主线 2 → 深度 1 → 主线 3 → 深度 2 → 主线 4 → 深度 3 → 深度 4 → 深度 5。

**发布时间**：工作日 19 点到 22 点，周末中午或晚上。按你自己的数据调。

**合集**：第 2 期后把内容挂进同一个合集，分成"玩法"和"硬核"两个子系列。

**评论区置顶**：GitHub Release 下载地址加交流群号，固定话术，每期都放。

## 十一、看什么指标

播放量不用看。看这四个：

1. **3 秒留存**。低于 40% 就重剪开头，别急着发下一期。
2. **完播率**。主线期目标 45% 以上，深度期 35% 以上就够了。
3. **评论区里带机型和报错的比例**。这个比点赞有用得多，它说明来的是真用户。
4. **Release 下载增量和进群人数**。这才是转化。

第 1 期发布后 24 小时只看 3 秒留存和完播率，不要同时改封面和标题，不然说不清是哪个起了作用。

## 十二、发布前必须先做的两件事

**补一次真机验收。**
公开的 v0.2.3 发行说明里写着，这个正式包还没做过真机验收，故障机启动、前端下载导入、角色卡和世界书对话、生图质量、认证 Local API 都还没测。引流引来的第一批用户如果首屏就崩，口碑收不回来。这次验收本身也是你最好的素材来源，全程录下来，后面几期的分镜都从这里切。

**改掉发版流程。**
v0.2.1 的发行资源曾经被原地替换过两次，文件名没变、哈希变了。这件事和项目主打的"哈希可校验"直接冲突，玩机区的观众真的会去核对。以后发版一律用新 tag，不覆盖已有资源。
