## 1. Process/owner chain (what actually executes)

```
AppStartupViewModel (APP/AppStartupViewModel.kt:104-117)
  -> McaAppContainer (APP/composition/McaAppContainer.kt:140)
     -> sharedRuntimeSupervisor (lazy, McaAppContainer.kt:256-262)
     -> engine: McaInferenceService (APP/composition/MainRuntimeAssembly.kt:62-66)
        -> container.createInferenceService (McaAppContainer.kt:576-580)
        -> McaInferenceService(application, runners, installationScopeId)
           (APP/composition/McaAppContainerApiParts.kt:314-322)
        -> runners = IsolatedLocalChatRunners (all RemoteLocalChatRunner)
           (McaAppContainer.kt:572-574; APP/IsolatedLocalChatRunners.kt:15-31)
     -> chatExecutionFacadeFor(engine) (McaAppContainer.kt:147-156)
        -> ChatExecutionFacade(supervisor, chatExecutionBodyFor(engine))
        -> ChatExecutionOwner.stream -> engine.streamChat
           (APP/ChatLocalApiProviderOperations.kt:110-126)
     -> imageExecutionGate = ImageExecutionOwner(sharedRuntimeSupervisor)
        (McaAppContainer.kt:264-271)
```

- The chat facade, image gate and supervisor are fields of **one container instance**, not of `McaApplication`. `McaApplication` only installs trust/lifecycle observers and holds no container (`APP/McaApplication.kt:53-77`). The "process-wide" wording in the KDoc is therefore a composition guarantee for the normal startup path, not a language-level singleton; constructing a second `McaAppContainer` creates a second supervisor/engine/facade (the class is `internal`, but tests and any future second startup path can do it).
- UI and Local API both reach the same facade: UI builds a `ui-<runId>-<uuid>` request id and calls `LocalApiRuntime.streamChat` (`APP/ChatExecutionOperations.kt:310-333`); the Local API foreground service installs the provider that calls `port.chatExecutionFacade.streamChat` (`APP/ChatLocalApiProviderOperations.kt:50-100`). The `ChatImagePromptBridgePort.streamChatLocal` path also calls the facade directly (`APP/ChatExecutionPortAdapters.kt:392-395`).
- Negative evidence: `BackendRuntimeOwner` is **not** registered with the supervisor. `grep -R "registerBackend("` finds only `RuntimeSupervisor.kt:176` and tests; `grep -R "getBackend("` likewise. The supervisor owns request identity/terminal records, not native engine mutual exclusion. Native mutual exclusion is `McaInferenceService.mutex` / `EngineLifecycleLease`.

## 2. RuntimeSupervisor — admission, identity, exactly-once terminal

- Creator: `sharedRuntimeSupervisor` is lazily created by the container (`McaAppContainer.kt:256-262`). Users: `ChatExecutionFacade` (`APP/facade/ChatExecutionFacade.kt:53-62`) and `ImageExecutionOwner` (`APP/facade/ImageExecutionGate.kt:62-66`), both holding the same container supervisor; `McaAppContainer.kt:268-271`.
- Admission: `admitRequest(requestId, consumer)` runs under `lifecycleLock`, returns null after shutdown, and in one transaction assigns `RequestIdentity(requestId, attemptId=attemptSequence.incrementAndGet(), runtimeEpoch=current)` then `register`, cancel-handle registration, optional callback-route subscription, and `Accepted` (`ENG/runtime/RuntimeSupervisor.kt:79-113`). Duplicate live id is rejected by `RequestRegistry.register` (`ENG/runtime/RequestRegistry.kt:104-110`). Failure inside admission rolls back all reservations (`RuntimeSupervisor.kt:104-111`).
- Identity: `RequestIdentity` carries `requestId`, monotonic `attemptId`, runtime epoch, session generation, worker incarnation, native sequence and trace id (`CON/RequestIdentity.kt:21-28`); `RequestSnapshot` exposes that full identity (`ENG/runtime/RequestRegistry.kt:14-21`). This is the only identity source an Agent adapter should record after admission.
- Terminal: `settleRequest` requires a terminal state, CAS-settles the exact attempt, then `releaseRequestResources` unregisters the cancel handle, archives the bounded outcome, unsubscribes the route and evicts the live entry (`RuntimeSupervisor.kt:129-164`); `RequestRegistry.settle` is exactly-once via `terminalReached` + legal transition (`RequestRegistry.kt:144-161`). `RequestState`'s legal graph is `Accepted -> Preparing -> Running`, `Running -> CancelRequested -> Cancelled`, with `Failed`/`Aborted` allowed from the active states (`CON/RequestState.kt:109-121`).
- Cancel: `RequestCancellationController.requestCancellation(requestId)` targets whichever attempt currently owns the id; the `RequestIdentity` overload is attempt-checked (`ENG/runtime/RequestCancellationController.kt:81-94`). `cancelAllActive` marks every tracked handle (`:166-172`); `cancelAllActiveBefore(epoch)` only older epochs (`:178-184`). Marks are bookkeeping; they do not cancel coroutines or call native stop.
- Release/shutdown: `shutdownProcess` closes admission, cancels/drains/clears requests, then closes every registered backend and rethrows the first close failure (`RuntimeSupervisor.kt:216-252`). **No production caller exists**: `grep -R "shutdownProcess("` finds only the definition, `close()`, and tests. `MainViewModel.onCleared` does not call it (`APP/MainViewModel.kt:463-470`).
- Process-death recovery: none. The registry, epoch counter, cancel handles and route archive are in-memory (`RuntimeSupervisor.kt:26-41`); process death discards them. There is no persisted request/lease/terminal table.
- Failure branch: `registerBackend` after shutdown closes the rejected backend and throws (`RuntimeSupervisor.kt:176-185`); shutdown attempts all backend closes and rethrows the first failure (`:232-251`).
- Consequence for Agent: supervisor admission is identity/terminal authority only. It cannot prove native exclusion, and its `stop` flags cannot stop a native runner by themselves.

## 3. ChatExecutionOwner — one admitted attempt, settled once

- Creator: one owner per facade (`ChatExecutionFacade.kt:58`); facade one per container (`McaAppContainer.kt:147-156`). User: every UI/Local API/worker chat turn through `stream` (`ENG/ChatExecutionOwner.kt:29-56`).
- Admission/streaming: `stream()` calls `supervisor.admitRequest(context.requestId, TERMINAL_ROUTE_CONSUMER)` **synchronously at call time**, then calls `body.stream(...)` and wraps it (`ChatExecutionOwner.kt:69-92`). The first event advances `Accepted/Preparing -> Running` (`:82-88,116-125`). The caller keeps the event flow; the admitted route consumer is intentionally a no-op (`:226-227`).
- Terminal mapping (exactly once, from `onCompletion`): `CancellationException -> Cancelled`; any other throwable -> `Failed`; last `GenerateEvent.Error` whose code/category is cancellation -> `Cancelled`; other error event -> `Failed`; otherwise `Succeeded` (`ChatExecutionOwner.kt:127-182`). Cancelled goes through `CancelRequested` first; success/failure first advances to `Running` so the terminal transition is legal (`:141-147`). `settleWithError` settles, records the bounded outcome, then releases resources in `finally` (`:184-206`).
- `stopGeneration()`: marks **every** live attempt cancelled in the shared supervisor and then calls the body's unconditional stop (`ChatExecutionOwner.kt:98-101`). Because the supervisor is shared with images, this marks image requests too (bookkeeping only; see §5).
- `stopGenerationIfActive(requestId)`: rejects blank, marks the supervisor attempt by request id, then asks the engine to stop only the matching token (`ChatExecutionOwner.kt:107-114`). It is request-id scoped, not `RequestIdentity` scoped; attempt safety depends on never reusing a live request id.
- Cancellation codes: `REQUEST_CANCELLED`, `CANCELLED`, `CANCELED`, `CNC_USER_CANCELLED`, `CNC_ALREADY_CANCELLED` (`ChatExecutionOwner.kt:208-224`). The engine emits `REQUEST_CANCELLED` from its decode loop when its stop token matches (`ENG/McaInferenceStreamDecode.kt:238-243`).
- Failure/leak branch: admission happens before `body.stream` and outside any `try`; if `body.stream(...)` throws synchronously, or the returned `Flow` is never collected, `onCompletion` never runs, so the `Accepted` entry, cancel handle and callback route stay registered until process death (`ChatExecutionOwner.kt:69-91`; no catch at `:80`). The Agent adapter must collect immediately and settle explicitly on construction failure, as the architecture doc already requires.
- Process-death recovery: none beyond the worker-session recovery in §7; owner state is in-memory.

## 4. ChatExecutionFacade — command surface and its exact limits

- `streamChat(request, context)` delegates to the owner (`APP/facade/ChatExecutionFacade.kt:93-94`); admission is therefore synchronous before the function returns. `dispatchChat` is the identity-only admission entry (not an execution path) (`:80-86`).
- `stopGeneration()` delegates to the owner's unconditional path (`:100-102`). `stopGenerationIfActive(requestId)` delegates and applies `?: false` to a non-null `Boolean` (`:108-109`), i.e. an always-left-elvis warning, not a nullable result.
- `cancelChat(requestId)` only marks supervisor cancellation (`:115-117`); it never calls `engine.stopGeneration*`. It is therefore **not a native cancel**. The attempt-checked overload takes `RequestIdentity` (`:124-126`). Neither overload has a production caller: `grep -R "\.cancelChat("` finds only tests (`app/src/test/.../Facade*Test.kt`).
- `snapshot(requestId)` reads the live registry, then falls back to the bounded terminal record after eviction (`:144-148`); `terminalOutcome` exposes the record directly (`:156`). Both return `RequestSnapshot`/`TerminalDeliveryRecord` and are query-only. `grep -R "\.snapshot(requestId"` / `\.terminalOutcome\(` finds no production caller today; `FacadeTerminalCleanupTest` is the only exercise.
- `settleStreamFailure(identity, reason)` attempt-checks cancel then settles `Failed` (`:167-172`); no production caller (`grep -R "settleStreamFailure("` only tests).
- Failure branch: shutdown or duplicate live id throws `IllegalStateException` from `streamChat`/`dispatchChat` (`:81-84`, `:93-94`; supervisor `:83`, registry `:107-109`).
- Exactness limits: the facade exposes no attempt handle from `streamChat`; a caller gets only a `Flow`. Identity must be obtained via `snapshot(requestId)` after the flow starts (and that method has no production consumer yet). The KDoc claim that `snapshot` is the identity lookup is consistent with the code (`RequestSnapshot.identity`), but it is an unused API in production.

## 5. Container/composition — engine construction and facade scoping

- Container creation: `AppStartupViewModel` constructs `McaAppContainer(app)` inside startup, then constructs `MainViewModel` with that container (`APP/AppStartupViewModel.kt:104-117`). Container lifetime is tied to the main ViewModel/startup handoff, not `Application`.
- Engine creation: `MainRuntimeAssembly` is the single app-side construction point; its `engine` property is `injectedEngine as? McaInferenceService ?: container.createInferenceService(runners = container.isolatedLocalChatRunners.runners, installationScopeId)` (`APP/composition/MainRuntimeAssembly.kt:55-66`). The container factory builds `McaInferenceService(context, runners, installationScopeId)` (`McaAppContainer.kt:576-580`; `McaAppContainerApiParts.kt:314-322`). `isolatedLocalChatRunners` is lazy (`McaAppContainer.kt:572-574`) and maps every runtime to `RemoteLocalChatRunner` (`APP/IsolatedLocalChatRunners.kt:15-31`).
- `chatExecutionFacadeFor(engine)` uses `AtomicReference.updateAndGet { existing ?: ChatExecutionFacade(sharedRuntimeSupervisor, chatExecutionBodyFor(engine)) }!!` (`McaAppContainer.kt:147-156`). The **first** engine wins; a later call with a different engine silently returns the facade bound to the first engine. Production call sites all pass the same engine: `McaAppContainerChatParts.kt:136,161` and `McaAppContainerApiParts.kt:245`.
- `sharedRuntimeSupervisor` is lazy and shared with `imageExecutionGate` (`McaAppContainer.kt:256-271`). `McaAppContainerCoordinatorParts.kt` does not construct or reference the chat facade; it only passes the engine into coordinator factories (e.g. `:78-141`, `:267-355`, `:451-511`), so the E06 facade wiring is exclusively in `ChatParts`/`ApiParts`.
- Failure branch: constructor/assembly failure in `AppStartupViewModel` is caught and records a startup diagnostic; previous startup is marked `starting` and the next launch shows a problem instead of resuming (`APP/AppStartupViewModel.kt:88-95,135-143`).
- Release/process death: `MainViewModel.onCleared` cancels one bridge job, releases Local API ownership, closes the image worker client and closes `isolatedLocalChatRunners`, but it does **not** call `supervisor.shutdownProcess()` or `engine.shutdown()` (`APP/MainViewModel.kt:463-470`). `engine.shutdown()` is called only by tuning/QAIRT worker services (`TuningProbeWorkerService.kt:616`, `QairtDryRunWorkerService.kt:230`). The main engine's native teardown is therefore process death or worker process teardown, not an orderly engine shutdown.
- Scoping caveat: `McaAppContainer` is not stored on `McaApplication`; if startup is retried or a second `MainViewModel`/container is constructed in the same process, the "one supervisor for the process" invariant is not enforced. `UNVERIFIED` whether production can hit that path.

## 6. McaInferenceService, lease, stop token and stream body

Fields and public entry points:

- `mutex = Mutex()`, `generationStopGate`, `generationStopEpoch`, `activeGenerationStopTarget`, `stopRequestedToken` (`ENG/McaInferenceService.kt:44-50`); `streamChat`/`stopGeneration`/`activeGenerationStopToken`/`stopGenerationIfActive` are thin delegates (`:202-213`).
- `acquireExclusiveLifecycleLease(stopActiveGeneration=true)` delegates to `acquireExclusiveLifecycleLeaseImpl` (`:155-159`). The impl **stops the current generation first** when the flag is true, then does `mutex.lock(owner)` and returns `EngineLifecycleLease(this, owner)` (`ENG/McaInferenceProfileTransactions.kt:62-69`). The default is dangerous for an adapter; `false` is the only non-preemptive mode and is used by image memory handoff (`APP/RuntimeReleaseOperations.kt:79`), assistant memory and context compression (`APP/AssistantMemoryOperations.kt:69`, `APP/ContextCompressionCoordinator.kt:267`).
- `EngineLifecycleLease` is opaque: service + owner token + `leaseId`; `active`/`releasing` guard and `release()` delegate (`CON` file is `ENG/McaInferenceContracts.kt:215-230`). `releaseExclusiveLifecycleLease` requires the same engine, is idempotent through `active/releasing`, rolls back `lease.deferredAuthorization` if set, marks inactive and unlocks exactly that token (`McaInferenceProfileTransactions.kt:71-103`). `withLifecycleLock` refuses a lease that is invalid, released, from another engine, or whose token no longer holds the mutex (`:184-196`). No timeout is implemented in acquire; a caller that needs the 120 s bound must wrap `withTimeout` itself.
- `GenerationStopToken` is only `(epoch: Long, requestId: String)` (`ENG/McaInferenceContracts.kt:22-26`); `ActiveGenerationStopTarget` adds the concrete runner and the **collector Job** that owns it (`:28-33`). There is no attemptId in the token. `activateGenerationStopTargetImpl` increments the epoch, rejects a live/unproven owner, and may reclaim a dead collector's target (`ENG/McaInferenceStopControl.kt:80-102`; decision at `ENG/GenerationStopTargetAdmission.kt:26-53`). `clearGenerationStopTargetImpl` only clears the matching token (`:104-111`); lifecycle transitions invalidate epoch/target/stop-requested (`:114-119`).
- `stopGenerationImpl`: if an active token exists, stop exactly it and **return**; otherwise fall back to `runnerFor(activeRuntime).requestStop()` inside `withTimeoutOrNull(STOP_REQUEST_TIMEOUT_MS)` (`ENG/McaInferenceStopControl.kt:13-26`; `STOP_REQUEST_TIMEOUT_MS = 500L` at `ENG/McaInferenceContracts.kt:239`).
- `stopGenerationIfActiveImpl(expected)`: `null -> false` before suspension; token mismatch -> false; duplicate stop already in flight -> true without dispatch; otherwise mark `stopRequestedToken`, hop to IO, recheck target/token, and call `target.runner.requestStop()` (`:39-77`). A timeout yields `true` (`?: true` at `:75`), so **true means "stop dispatched/accepted", not "native execution confirmed stopped"**.
- Streaming body: `streamChatImpl` is a cold `flow` that takes `mutex` when no lease is supplied (`ENG/McaInferenceStreamChat.kt:17-25`; `withLifecycleLock` at `McaInferenceProfileTransactions.kt:184-196`); with a lease it verifies ownership without re-locking. It emits explicit error events for no loaded model (`:55-59`), context-length rejection (`:73-87`), worker-session loss requiring explicit reload (`:27-42`), and native begin failure (`:253-264`, `:348-364`). It activates the stop token immediately before native work (`:219-224`) and clears it in `finally` under `NonCancellable + io` (`:408-420`); the outer `finally` rolls back an uncommitted profile and calls `parameterCoordinator.finishRequest(requestId)` (`:422-444`).
- Failure/cancel branch: decode loop sees `stopRequestedToken == generationStopToken`, emits `GenerateEvent.Error(code="REQUEST_CANCELLED")`, and returns early (`ENG/McaInferenceStreamDecode.kt:238-243`); the owner maps that to `Cancelled` (`ChatExecutionOwner.kt:137`).
- Process-death recovery: the mutex, lease objects, stop token/epoch and pending transactions live only in the engine instance. The native model lives in the `:local_chat` worker process (§7). Process death discards leases; there is no persisted lease table (by design per architecture §5.2.1), so recovery must be worker-owner reconciliation, which does not exist for a new main process beyond `workerSessionLost`.

## 7. Local API, chat worker process boundary, BackendRuntimeOwner

Local API:

- `LocalApiRuntime` is an in-memory `object` singleton (`API/LocalApiRuntime.kt:10-14`). `claimOwner(token, onReplaced)` installs a token and runs the replaced owner's cleanup; `releaseOwner(token)` clears providers, published bindings, trace state and token only if the token still matches (`:20-64`). `LocalApiRuntimeOwner` is a thin delegation wrapper (`APP/LocalApiRuntimeOwner.kt:14-31`); `MainViewModel` claims it with its `localApiRuntimeOwner` token and publishes providers (`APP/MainViewModel.kt:247-252`), and releases it in `onCleared` (`:463-467`).
- Provider funnel: `LocalApiRuntime.streamChat(request, executionContext)` reads `publishedBindings` (falling back to live fields) and invokes `streamChatWithContextProvider` then legacy provider (`API/LocalApiRuntime.kt:215-243`); stop calls `stopGenerationProvider` / `stopGenerationIfRequestActiveProvider` and returns false when absent (`:245-256`). The app installs these to the facade (`APP/ChatLocalApiProviderOperations.kt:50-100`).
- Failure branch: UI callers treat a null flow as fatal (`APP/ChatExecutionOperations.kt:319-333`, `?: error(...)`); a missing stop provider returns false. Owner replacement runs the previous cleanup (`LocalApiRuntime.kt:20-33`). No persisted owner across process death.
- Process boundary: `LocalApiForegroundService` has no `android:process`, so it runs in the main process (`app/src/main/AndroidManifest.xml:159-167`). It can recreate the listener on a null intent when prefs say enabled (`APP/LocalApiForegroundService.kt:74-79`), restarts itself after an overlapping stop (`:111-142`), and owns the loopback server (`:194-208`, `:258-273`). It does **not** restore `LocalApiRuntime` owner/providers; those are MainViewModel's job. `grep` shows no recovery code in the service.

Chat worker:

- `LocalChatWorkerService` runs in `:local_chat`, `stopWithTask=false`, specialUse FGS (`AndroidManifest.xml:120-132`); the main process always holds `RemoteLocalChatRunner`s (`APP/IsolatedLocalChatRunners.kt:15-31`). The worker binder performs init/load/unload/stats and generation calls (`APP/LocalChatWorkerService.kt:94-104`), with `requestStop()` dispatching runner stop via a disposable thread and arming forced recovery for MNN (`:334-352`), and `requestStopIfActive()` returning false when no worker-side stage is active (`:354-369`).
- Worker process teardown: `shutdown()` stops/unloads/shuts down the runner, leaves foreground, `stopSelf` (`:427-445`); `recycleForReplacement()` additionally `Process.killProcess(Process.myPid())` and the caller treats Binder death as recycle acknowledgement (`:447-469`); `onDestroy` clears watchdogs, runners and native-operation state without synchronously entering native shutdown (`:501-523`).
- Process-death recovery (main side): `RemoteLocalChatRunner.isSessionKnownLost()` is true if the worker flagged session loss or the model was loaded and the remote binder is gone (`APP/RemoteLocalChatRunner.kt:236-238`); it retains a Binder death observer for disposable workers (`:32-43,350-361`). The next `streamChatImpl` checks `isolatedWorkerSessionNeedsReload || isolatedWorkerSessionLostLocked()` and either auto-reloads or emits an explicit "reload model" error (`McaInferenceStreamChat.kt:27-54`; detection at `ENG/McaInferenceLoadRecovery.kt:326-347`). The main process restart itself creates a new container/engine; no request/lease is restored.
- No client-death watcher is visible in `LocalChatWorkerService` (unlike image/Qairt/tuning workers). If the main process dies, `stopWithTask=false` means the worker process is not automatically tied to the task; stale-worker survival and its native memory are `UNVERIFIED` and must be reconciled by the future Agent/worker owner before a new run.

BackendRuntimeOwner (state explicitly, because doc and source differ):

- `ENG/runtime/BackendRuntimeOwner.kt` KDoc says "skeleton, no native loader" and "not constructed by production code" (`:13-19`). The default `createEngine` returns a bookkeeping-only `EnginePort` whose `isReady` is always false (`:76-98`); session id conflicts are rejected rather than replacing a live session (`:99-113`); `releaseEngine`/`shutdown` close tracked engines and aggregate failures (`:149-173`). This default path has **no production authority** and is exercised only by tests.
- However, the blanket KDoc statement is stale: production `MnnCpuChatRunner` constructs `BackendRuntimeOwner(backendKind="MNN_CPU", engineFactory = { ... MnnChatEnginePort ... })` (`ENG/LocalRunnerShells.kt:392-415`) and releases superseded engines through it (`:442-448`). So it is a private per-runner engine bookkeeping owner for MNN, using the real `MnnChatEnginePort` factory; it is still not registered with `RuntimeSupervisor` and is not a process-wide native authority.
- Failure branch: if `engineFactory` is absent, `createEngine` returns a non-ready engine (callers must fail explicitly); if the factory path is used, `createEngine` returns the real port (`BackendRuntimeOwner.kt:80-84`). The supervisor's `registerBackend` rejection path (`RuntimeSupervisor.kt:176-185`) is not used by production.

## 8. Image path — gate, coordinator, lease handoff, foreground keepalive

- Identity gate: `ImageExecutionGate` is the interface every local image operation passes through (`generate` at `APP/LocalImageWorkerClient.kt:208-217`, `upscale` at `APP/LocalImageWorkerClientUpscale.kt:18`). `ImageExecutionOwner.run` admits into the **same** supervisor, drives `Preparing -> Running`, settles `Succeeded`, or `Cancelled` for `CancellationException`/`LocalImageWorkerCancelledException`, or `Failed` with a typed envelope for anything else (`APP/facade/ImageExecutionGate.kt:62-93`). Shutdown makes `admitRequest` return null and the gate throws its own `IllegalStateException` (`:68-72`); a duplicate live request id instead throws from `RequestRegistry.register` (`ENG/runtime/RequestRegistry.kt:104-110`). `cancel(requestId)` only marks supervisor cancellation (`:96-102`); it does not cancel the worker.
- Product serialization: `LocalImageGenerationCoordinator` is an in-process single-lease mutex bound to `(requestId, epoch)`; `tryAcquire` returns null when busy, `release` only accepts the identical lease object, and a stale lease release returns false (`APP/LocalImageGenerationCoordinator.kt:10-42`). Created by the container (`McaAppContainer.kt:237`); users are the UI `ImageGenerationOwner` and the Local API image gate (`APP/ImageGenerationOwner.kt:31-95`). This is **not** a native/worker lock and it is not visible from the image worker process.
- Native handoff: for a LOCAL image job, `ImageGenerationOwnerExecution` obtains `host.prepareLocalImageRuntimeMemory()` (`APP/ImageGenerationOwnerExecution.kt:102`), which calls `McaInferenceService.acquireExclusiveLifecycleLease(stopActiveGeneration=false)`, unloads the LLM with that lease, clears runtime admission state and rejects a pending profile (`APP/RuntimeReleaseOperations.kt:72-104`; host mapping at `APP/ImageGenerationWorkflowPortAdapters.kt:331-334`). This is how image avoids `stopGeneration` but still waits for the chat mutex.
- Release: the image execution's `finally` runs `withContext(NonCancellable)` -> `awaitOwnedWorkerRelease()` -> `chatRuntimeLease.release()` (`ImageGenerationOwnerExecution.kt:357-368`). The client's await waits for the owned image-worker Binder death and throws `image_worker_exit_unconfirmed` on timeout (`APP/LocalImageWorkerClient.kt:150-165`). The UI submit path also releases the coordinator lease and foreground lease in completion handlers (`APP/ImageGenerationOwner.kt:449-529`).
- Failure/cancel branch: a cancelled/failed local batch updates the job to `CANCELLED`/`FAILED`, returns early, and still releases the engine lease in `finally` (`ImageGenerationOwnerExecution.kt:243-273`); a commit failure distinguishes cancellation from other errors and only a cancellation deletes the produced copy (`:295-356`). Local API image contention throws `LocalApiImageOperationBusyException` before worker bind (`ImageGenerationOwner.kt:44-52`); cancellation cancels the request job and the worker (`:98-104`); release failure throws `"Local API image generation lease was replaced..."` (`:91-93`).
- Process boundary/recovery: image worker is `:local_image` (`AndroidManifest.xml:68-77`); it watches the client callback Binder and cancels on client death (`APP/LocalImageWorkerService.kt:163-172`, `:240-247`). Main-process death loses the coordinator and the engine lease. Startup image recovery is limited to the commit journal/library reconciliation (`McaAppContainer.kt:225-230`, `McaAppContainerChatParts.kt:73-90`); no local image generation is resumed.
- Foreground keepalive: `McaGenerationForegroundLeaseRegistry` serializes acquire/start and release/stop under one lock; a start failure removes the owner and rethrows (`APP/GenerationForegroundLeaseRegistry.kt:17-27`); release of the last owner stops the service, unknown lease returns false (`:29-33`); the current task snapshot is the last owner kind (`:36-39`). `McaGenerationForegroundService.acquire()` converts any `startForegroundService` failure to a `null` lease (`APP/McaGenerationForegroundService.kt:158-171`), and release is a no-op for null (`:173-184`). The service promotes a bootstrap notification in `onCreate` before the task is known (`:23-43`), re-promotes and stops itself on null intent/task (`:45-77`), returns `START_NOT_STICKY` (`:77`), and removes foreground on destroy (`:82-87`).
- Failure/death: a foreground start failure yields a null lease but does **not** abort generation; the notification may be absent. The registry is a process-local static map (`McaGenerationForegroundService.kt:153`), not persisted; process death loses all leases and the notification. `UNVERIFIED`: FGS/notification-permission behavior on targetSdk 36 devices, and whether a missing lease is surfaced to the user.

## 10. UNVERIFIED items (read-only limits)

- No Gradle build, unit test, native build, adb/device run or app execution was performed. All statements are static source evidence at the baseline blobs.
- Per-backend native stop semantics (`runner.requestStop()` landing in JNI, MNN/QNN/LiteRT worker exit) are not verified. Kotlin-level `true` from `stopGenerationIfActive` is dispatch/acceptance only, not native return evidence.
- `stopGenerationIfActiveImpl`'s 500 ms timeout returns `true` even when the recheck or `requestStop` did not complete (`McaInferenceStopControl.kt:58-76`); the true meaning is "stop was accepted by the control path", not "native generation stopped".
- The architecture's 120 s resource-wait cap is not implemented in `McaInferenceService.acquireExclusiveLifecycleLease`; it must be a caller-side `withTimeout`. No production call site currently imposes it.
- `ChatExecutionFacade.cancelChat`, `settleStreamFailure`, `terminalOutcome`, `snapshot` and `isChatActive` have no production callers according to repository grep; they are exercised only by app tests. The Agent plan's use of `snapshot` to obtain admission identity is supported by the return type but has no production precedent.
- No production code calls `RuntimeSupervisor.shutdownProcess()`; no production code closes the main `McaInferenceService` (only tuning/Qairt worker services). Orderly-shutdown behavior and supervisor drain are untested in production.
- `chatExecutionFacadeFor` ignores a second engine argument; whether any future Agent adapter passes an `existingEngine` different from the main engine is unverified. All three production calls pass the main engine.
- `McaAppContainer` is not held by `McaApplication`; the "one supervisor per process" claim is a composition invariant for the startup path, not a runtime-enforced singleton. Multiple containers/MainViewModels in one process would create parallel supervisors.
- `LocalChatWorkerService` has no visible client-Binder death recipient for chat work (unlike image/Qairt/tuning). Stale worker survival after main-process death, and its native memory, is unverified.
- Notification-permission/targetSdk/FGS start rejection behavior is only source-level (`McaGenerationForegroundService.acquire` returns null); no device evidence.
- The Local API foreground service can restore the listener before `MainViewModel` re-claims owners/providers, so HTTP behavior in that window is unverified.
- The `?: false` on `chatExecutionFacade.stopGenerationIfActive` (`ChatExecutionFacade.kt:108-109`) is an always-non-null elvis; no behavioral difference, but it is a code smell and could hide a future nullable change.
- The stale `BackendRuntimeOwner` KDoc ("not constructed by production code") contradicts `MnnCpuChatRunner` construction with a real `engineFactory` (`LocalRunnerShells.kt:404-415`); only the default skeleton path is production-unused.

## 11. Facts the Agent V1 plan assumes but this source does not prove

- "Wait up to 120 s for the resource" is plan-level only; the engine lease waits indefinitely and has no timeout/status (`McaInferenceProfileTransactions.kt:62-69`).
- "Stop returns native evidence" is not true at this layer. `true` is dispatch/acceptance; `stopRequestedToken` dedupes duplicates but does not mean the native call returned (`McaInferenceStopControl.kt:39-77`).
- "Cancel by requestId cancels the generation" is only true through `facade.stopGenerationIfActive`/`stopGeneration`; `cancelChat` alone only marks the supervisor (`ChatExecutionFacade.kt:115-117`) and the chat flow does not consult the supervisor cancellation flag (`ChatExecutionOwner.kt:81-91`). An Agent adapter must use the engine-backed stop, not `cancelChat`.
- "Agent attempt is isolated from UI stop" is not guaranteed by the shared supervisor: UI stop calls `cancelAllActive` on the same supervisor that would admit Agent attempts (`ChatExecutionOwner.kt:98-101`; `RuntimeSupervisor.kt:40,226`). The flag is bookkeeping and does not cancel work, but any Agent code that reads supervisor cancellation would observe it.
- "Facade returns an identity handle" is false: `streamChat` returns only `Flow<GenerateEvent>` (`ChatExecutionFacade.kt:93-94`). Identity is obtainable only from `snapshot(requestId)`/terminal records after admission, and `snapshot` is not used in production.
- "The supervisor is native authority / process-wide" is not proven. It is a per-container identity/terminal owner; native authority is the engine mutex/lease and the `:local_chat` worker process (`McaAppContainer.kt:256-262`; `McaInferenceProfileTransactions.kt:62-69`; `AndroidManifest.xml:120-132`).
- "The facade can bind a new Agent engine" is not supported: first engine wins (`McaAppContainer.kt:147-156`); an Agent adapter must reuse the existing main engine instead.
- "Process death recovery exists" is not proven for chat/Agent runs. Only chat worker session loss (`workerSessionLost` -> reload) and image commit journal reconciliation exist; there is no persisted request/lease recovery.
