# MCA v0.3.8

**llama.cpp 升级到 v0.9.0：跨 999 个上游提交的补丁重基线，本地推理链路已真机验证**

- 发布日期：2026-11-05
- 上一版本：`v0.3.7`（versionCode 16）
- 本版本：`0.3.8`（versionCode 17）
- 适用设备：Android `arm64-v8a`，minSdk 26
- 许可证：**Apache-2.0**

---

## 1. llama.cpp 基线

- `third_party/llama.cpp` 从 `4ceb1719`（`b11105+6`，2026-09-22）升级到上游 **`v0.9.0`**（`cd959bae`，2026-11-04），跨度 999 个提交。
- 版本号进入运行时身份：`llama.cpp@cd959bae99ff4bed22bef2604f45241c09bbb8c8+mca-stq1_0`。
- `vendor/llama/llama-vendor.properties` 记录新基线、三个补丁的来源与 SHA-256。
- **新增基线校验**：`applyMcaLlamaPatches` 在打补丁前校验子模块 `HEAD` 必须等于清单里的 `baseCommit`，否则直接失败。此前该任务不校验基线，补丁会被静默打到错误的提交上。

## 2. 三个补丁的重基线

- `llama-stq1_0.patch`（上游 PR #22836，1.25-bit 三值量化）：上游在同一个枚举位插入了 `F8_E4M3`，因此 `STQ1_0` 顺延到 `44`、`GGML_TYPE_COUNT` 到 `45`，`llama_ftype`、`gguf-py` 同步顺延。
- `llama-kleidiai-kquant-fallback.patch`：上游在此期间为 KleidiAI 补上了 **Q4_K / Q6_K** 内核，原补丁的能力门（只认 Q4_0/Q8_0/F32）会把这些类型踢出加速路径。新补丁的门跟随上游内核集合（Q4_0 / Q4_K / Q8_0 / Q6_K / F32），保留「缓冲回调不得给不支持的类型挂 traits」这一防御。
- `llama-vulkan-no-coopmat.patch`：仅注释位置冲突，语义不变。

## 3. MCA 侧适配

- `common_batch_add` / `common_batch_clear` 被上游删除（改为 `common_batch` 包装 `llama_batch_ext`），但 `llama_batch` 与 `llama_decode()` 未变。新增 `llama_batch_compat.hpp`，按上游原语义提供两个内联助手，解码路径不改。
- `common_speculative_process()` 改为接收 `common_batch`：投机解码校验批次按 token 条目镜像过去，嵌入视图留空（该路径只跑纯 token 批次）。
- `common_chat_templates_apply()` 返回 `common_chat_prompt`，取 `.str()` 得到扁平文本。
- `mca_mtmd` 的显式源文件清单补入上游新增的 12 个 clip 图实现（chatterbox / lfm3a / lfm3vl / ling3vl / muse-spark-audio / nemotron-omni / nemotron-transcribe / sensenova-u1 / soprano / voxtral-rt），否则新类的 vtable 在链接期缺失。

## 4. 其余推理引擎（本轮不动）

- **MNN**：上游已有 3.6.2，但 MCA 固定在 3.6.1 且带 34 个文件的 `mca-mnn-3.6.1.patch` 与 vendor 校验戳。重基线风险落在图融合、prompt cache、投机解码这些直接影响出词的路径上，按「影响使用则不更新」保留 3.6.1。
- **GenieX**：已是上游最新 `v0.10.0`。
- **tokenizers-cpp**：上游最新发布仍是 `v0.1.1`，无新版本可跟。
- **stable-diffusion.cpp / ggml**：固定在 `3f3d36f7` 并带 Wan 5D 补丁，动它要重验生图全链路，保留。
- **QAIRT/QNN**：本机 SDK `2.45.0.260326`，升级需要新 SDK 与 HTP 重新验证，保留。
- **LiteRT-LM**：`0.16.1` 受 SBOM 门禁固定，未做跨版本验证前不升。
