## 0. 紧急修复

### 0.1 发送消息报「Row too big to fit into CursorWindow」

现象：点发送弹出「发送失败：Row too big to fit into CursorWindow requiredPos=0,
totalRows=3」，挂不挂预设都会出现。

原因：`chat_sessions` 表里单行 JSON（角色卡快照 / 外观 / 上下文摘要，酒馆角色卡常内嵌
整本 lorebook）超过 Android CursorWindow 的约 2 MB 上限，于是 `SELECT * FROM
chat_sessions` 连第一行都装不进窗口 —— 所有会话读取（含发送路径）一起失败。预设只是
在那段时间被操作过，不是触发原因。

修复（**不截断任何用户数据**）：

- 超过 192 KiB 的文本/JSON 写入 app 私有文件，行里只保留一个小的引用标记；
  读取时自动还原原文，文件缺失时如实报告而不是让整表读取失败
- 覆盖 6 张表 13 列：会话文档、角色卡与预设参数、消息正文与推理内容、
  角色记忆与记忆轮次、文件索引文本。真机上最常见的触发点其实是**角色记忆与
  记忆轮次**——它们只在生成前读取，所以启动正常、一发送就失败
- 启动时、Room 打开之前做一次幂等修复：先用 `length()` 找出超限行，再用
  `substr()` 按 32 KiB 切片读回原文（每片都远小于窗口，这是唯一能读出超限行的
  办法），然后写回引用；用 `rowid` 定位，复合主键表也适用
- 每次启动写一条 `large_row_offload repaired=N failed=M` 日志，便于确认修复结果
- 不做数据库迁移，旧数据无需前向修复；写失败的极端情况保留原值而不是丢数据

### 0.2 预设名显示成 `document:1000156859`

导入预设时用 `uri.lastPathSegment` 当兜底名，而 SAF 的 lastPathSegment 就是文档 id。
现在取名优先级为：预设文件内 `name` → 真实文件名（DISPLAY_NAME）→ 规范化后的
lastPathSegment → 「模型预设」；失败提示也走同一套规范化。非法的纯数字、纯 URI、
空白一律回退，不再把 provider 语法写进持久化。

## 1. 聊天：角色可用的本地轻工具

新增三个**零副作用**工具，走与 DSH 同一套提示词工具协议（因为 OpenAI 兼容 / Anthropic
传输与本地 llama.cpp runner 都不会序列化 `ChatRequest.tools`）：

- `get_device_time` —— 云端链路此前完全没有时间信息，角色现在能读到真实日期、时间与时区
- `calc` —— 自写递归下降求值器：只认数字、五个运算符、括号与固定函数表，不用
  `ScriptEngine`、不 `eval`；除零、负数开方、溢出都是显式失败
- `roll_dice` —— `NdM±K`，次数与面数有硬上限

边界：每次最多 2 个调用、最多 1 轮续答；协议标记在流式阶段就被门控拦住，永不进入聊天
记录；工具名未知或信封非法时静默降级为普通回答，**绝不让工具失败一次发送**。工具说明
注入请求级系统上下文，磁盘前缀缓存显式排除这段文本，因此不会让角色前缀缓存失效。

开关在 设置 → 实验功能 → 聊天本地工具，默认开启。

## 2. 缓存：云端提示词缓存 + 复用可观测性

- **云端**：Anthropic 请求的稳定系统前缀现在带 `cache_control: ephemeral`（此前一行都
  没有，等于完全不缓存）；openai.com 侧附带 `prompt_cache_key`（会话 id 的 sha256 前
  32 位，原始 id 不上线，其它网关一律不带，避免严格网关 400）
- **缓存 token 上报**：解析 Anthropic `cache_read_input_tokens` 与 OpenAI
  `prompt_tokens_details.cached_tokens`，进入统一统计
- **可观测性**：此前 native 已回传命中/未命中却没有任何展示，用户无法判断 1 GiB 前缀缓存
  值不值。设置 → 隐私与数据 现在显示命中率、命中/尝试次数、复用 token 与未命中主因；
  只统计真正产生观测的轮次，云端未上报即不记失败

## 3. 折叠屏 / 平板：与手机同一套布局

这一版**不做大屏导航重排**。折叠屏、平板与手机使用完全相同的布局与导航：抽屉仍是
抽屉、分段条仍是分段条、视频页仍是单列、DSH 仍是单 WebView。宽屏只意味着"同样界面
用更大的窗口显示"，而不是另一套前端。

初版曾把宽屏改成常驻侧栏/左右双栏，实测在平板上属于"前端变了"，已整体回退
（见提交 `revert(ui)`）。后续若要做大屏增强，只会做不改变现有结构的增量，
并且先确认再动手。
